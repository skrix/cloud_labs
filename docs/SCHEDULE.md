# Schedule

Мінімальна кількість задач API залежить від часу доби: **вдень** сервіс тримає запас із двох
задач, **вночі**, коли навантаження мале, — одну. Autoscaling (завдання 1) працює поверх
розкладу: розклад змінює лише нижню межу, а додавати задачі під навантаженням autoscaler може в
будь-який час.

Terraform: [`deploy/aws/terraform/schedule.tf`](../deploy/aws/terraform/schedule.tf).

| Сервіс | День (08:00–22:00 Kyiv) | Ніч (22:00–08:00 Kyiv) | Максимум |
|--------|-------------------------|------------------------|----------|
| API    | **2**                   | **1**                  | 4        |
| Worker | 1                       | 1                      | 4        |
| Redis  | 1                       | 1                      | 1        |

## Як це зроблено

- **Scheduled actions** Application Auto Scaling (`aws_appautoscaling_scheduled_action`):
  `api_day` о 08:00 ставить `min_capacity = 2`, `api_night` о 22:00 — `min_capacity = 1`.
  Час — за `Europe/Kyiv` (`schedule_timezone`), тож перехід на літній час враховується.
- Вранці, якщо задач менше за новий мінімум, autoscaler одразу додає другу. Ввечері зайву задачу
  знімає target tracking, коли CPU 15 хв нижче за поріг scale-in (як після load test,
  [AUTOSCALING.md](AUTOSCALING.md)).
- **`lifecycle { ignore_changes = [min_capacity] }`** на scalable target API: інакше кожен
  `terraform apply` повертав би мінімум зі змінних, перебиваючи розклад.
- Параметри — змінні `schedule_enabled`, `schedule_day_cron`, `schedule_night_cron`,
  `schedule_timezone`, `api_day_min` (нічний мінімум — `autoscaling_min`).

### Чому вночі 1, а не 0

На ECS Fargate сервіс можна поставити на 0 задач, але **запит його не розбудить**: ALB без
жодної здорової цілі відповідає `503`, а target tracking за CPU не має метрики, від якої
стартувати (CPU нуля задач не існує). На платформах із масштабуванням до нуля за запитами
(Cloud Run, Azure Container Apps) запит сам запускає контейнер; на ECS для цього потрібна
окрема логіка. Тому вночі API — 1 задача.

Worker лишається на 1 задачі цілодобово: показання, прийняті вночі, записуються в базу за
секунди, без холодного старту worker'а (≈ кілька хвилин на метрики черги, alarm і запуск
задачі Fargate).

## Місячна економія

Ціни Fargate, Linux/x86, eu-north-1 (AWS Pricing API, листопад 2026): **$0,0445 за vCPU-год**,
**$0,0049 за ГБ-год**. Задача 0,25 vCPU / 0,5 ГБ:

```
0,25 × 0,0445 + 0,5 × 0,0049 = $0,013575 за задачу-годину
```

Місяць = 730 год (30,42 дня): **день** 14 год × 30,42 = **425,8 год**, **ніч** 10 год × 30,42 =
**304,2 год**.

Рахується лише **мінімальна** кількість задач — те, що працює завжди; задачі, які autoscaler
додає під навантаженням, однакові в обох варіантах.

| Варіант                                     | API, задачо-год            | Worker, задачо-год | Разом, год | $ / міс   |
|---------------------------------------------|----------------------------|--------------------|------------|-----------|
| Без розкладу: 2 задачі API цілодобово       | 2 × 730 = 1460             | 730                | 2190       | **29,73** |
| З розкладом: API 2 вдень, 1 вночі           | 2 × 425,8 + 304,2 = 1155,8 | 730                | 1885,8     | **25,60** |
| **Економія**                                | 304,2                      | —                  | 304,2      | **4,13 (−14 %)** |

Тобто нічна задача API, яку знімає розклад, економить 304,2 × 0,013575 = **$4,13 на місяць**
(−21 % вартості API).

**Порівняно з попередньою конфігурацією** (1 задача API цілодобово, $19,82 / міс разом із
worker'ом) розклад коштує на **$5,78 більше** — це ціна другої денної задачі. Вона дає запас на
пікове навантаження (масштабування займає ≈ 5 хв, [AUTOSCALING.md](AUTOSCALING.md)) і на
відмову однієї задачі: ECS розміщує дві задачі в різних зонах доступності. Вночі цей запас не
потрібен, і розклад його прибирає.

Без змін: Redis (1 задача, $9,91 / міс), RDS, ALB, SQS. Для порівняння: ті самі задачі на ARM
(Graviton, $0,0356 / $0,00392) коштували б на ≈ 20 % менше.
