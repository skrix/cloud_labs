# Load test

Сценарій k6: [`loadtest/script.js`](../loadtest/script.js), запуск —
[`loadtest/run.sh`](../loadtest/run.sh).

## Запуск

```sh
npm run loadtest                       # BASE_URL = terraform output url
BASE_URL=http://<alb-dns> VUS=100 npm run loadtest
```

k6 встановлюється в devcontainer ([`.devcontainer/post-create.sh`](../.devcontainer/post-create.sh)).
Перед стартом `run.sh` чекає до хвилини, поки відповідає `GET /api/health/db`. Звіт —
`loadtest/results/<час>/report.md`.

| Змінна        | Типово                 | Опис                                                      |
|---------------|------------------------|-----------------------------------------------------------|
| `BASE_URL`    | `terraform output url` | Адреса сервісу                                            |
| `VUS`         | `40`                   | N — віртуальних користувачів (VU) на сталому навантаженні |
| `RAMP_UP`     | `3m`                   | Наростання 0 → N                                          |
| `STEADY`      | `5m`                   | Стале навантаження                                        |
| `RAMP_DOWN`   | `2m`                   | Спад N → 0                                                |
| `THINK_TIME`  | `0.5`                  | Максимальна випадкова пауза між запитами, с               |
| `HISTORY`     | `1440`                 | Скільки показань кожного пристрою завантажує `setup`      |
| `DEVICE_RATE` | `0` (вимкнено)         | Сценарій devices, показань/с ([QUEUE.md](QUEUE.md))       |
| `DEVICES`     | `50`                   | Кількість пристроїв сценарію devices                      |

Швидка перевірка локально:

```sh
PORT=3100 npm start &
BASE_URL=http://localhost:3100 VUS=3 RAMP_UP=5s STEADY=15s RAMP_DOWN=5s npm run loadtest
```

## Сценарій

«Мало записів, багато читань»: ітерація VU — **1 запис і 9 читань**. Аналогія з постами:
пристрій надсилає показання («пост»), власник читає його, список, статистику і дані пристрою
(«автора»).

| #  | Запит                                       | Що імітує                                  |
|----|---------------------------------------------|--------------------------------------------|
| 1  | `POST /ingest`                              | запис: нове показання                      |
| 2  | `GET /user-devices/:id/readings/:readingId` | щойно створене показання                   |
| 3  | `GET /user-devices/:id/readings?limit=20`   | список показань                            |
| 4  | `GET /user-devices/:id`                     | дані «автора» (пристрій, модель, прошивка) |
| 5  | `GET /devices/:id`                          | модель з каталогу                          |
| 6  | `GET /user-devices`                         | свої пристрої                              |
| 7  | `GET /devices`                              | каталог                                    |
| 8  | `GET /firmwares?deviceId=`                  | прошивки моделі                            |
| 9  | `GET /user-devices/:id/readings/:readingId` | попереднє показання                        |
| 10 | `GET /user-devices/:id/readings/stats`      | статистика за 7 днів — найважчий запит     |

- **Фази:** 0 → N за 3 хв, N протягом 5 хв, N → 0 за 2 хв.
- **`setup`** (раз перед тестом, не вимірюється) створює користувачів, по пристрою на кожен VU і
  `HISTORY` показань на пристрій. Реєстрацію й вхід (bcrypt) винесено з циклу, щоб CPU визначали
  читання, а не хешування паролів. Від бази потрібен лише каталог пристроїв (сідер `catalog`).
- **Thresholds:** помилок < 1 %, p95 < 500 мс; рахуються лише запити фази навантаження.
- **З чергою** (завдання 6) `POST /ingest` відповідає 202 і показання з'являється в базі пізніше,
  тож запити 2 і 9 приймають і 404 — k6 рахує частку вже доступних.

### Вибір N

Один VU робить ≈ 4 запити/с. N має бути таким, щоб на сталому навантаженні CPU однієї задачі
перевищив 70 % і спрацювало масштабування.

| Прогін             | Версія                        | N   | CPU на сталому | Масштабування               |
|--------------------|-------------------------------|-----|----------------|-----------------------------|
| `20261108T222156Z` | без статистики                | 40  | 50–59 %        | ні                          |
| `20261110T100143Z` | статистика, 30 днів історії   | 60  | 85–100 %       | так                         |
| `20261110T105034Z` | статистика, історія в `setup` | 100 | 99–100 %       | так, наприкінці сталої фази |

Без статистики запити були надто легкі, тому її додано в сценарій. Поточна версія потребує
N = 100.

## Результати

Прогін [`20261110T105034Z`](../loadtest/results/20261110T105034Z/report.md), N = 100:

| Показник           | Значення                                        |
|--------------------|-------------------------------------------------|
| Запитів            | 85 780 (8 578 ітерацій)                         |
| Запитів за секунду | 131 у середньому; ≈ 160 на сталому навантаженні |
| Частка помилок     | 0,00 % (2 відповіді 502 з 85 780)               |
| Latency p50        | 254 мс                                          |
| Latency p95        | 599 мс (поріг 500 мс не витримано)              |
| Latency p99        | 872 мс                                          |
| Максимум задач ECS | 3                                               |

p95 вище порогу, бо ≈ 5 хв (від перетину порогу CPU до появи другої задачі) весь трафік
обслуговувала одна насичена задача — див. [AUTOSCALING.md](AUTOSCALING.md).

Дві відповіді 502 від ALB спричинив keep-alive таймаут Node, коротший за таймаут ALB. Це
виправлено в [`src/server.js`](../src/server.js); у пізніших прогонах ([CACHE.md](CACHE.md),
[QUEUE.md](QUEUE.md)) помилок немає.
