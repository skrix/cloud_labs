# Навантажувальне тестування

Сценарій: [`loadtest/script.js`](../loadtest/script.js) (k6), запуск —
[`loadtest/run.sh`](../loadtest/run.sh).

## Запуск

```sh
npm run loadtest                       # BASE_URL береться з terraform output url
BASE_URL=http://<alb-dns> VUS=40 npm run loadtest
```

k6 (v1.8.2) встановлюється в devcontainer скриптом
[`.devcontainer/post-create.sh`](../.devcontainer/post-create.sh). Результати зберігаються в
`loadtest/results/<час>/`: `report.md` (підсумковий звіт) і `summary.json` (усі метрики k6,
не комітиться).

Перед тестом `run.sh` перевіряє, що сервіс і база доступні (`GET /api/health/db`): до 12 спроб
з інтервалом 5 с (після деплою задача ще може виконувати міграції та сідери), інакше
завершується з помилкою, не запускаючи k6.

| Змінна            | Типово               | Опис                                                          |
|-------------------|----------------------|---------------------------------------------------------------|
| `BASE_URL`        | `terraform output url` | Адреса сервісу                                              |
| `VUS`             | `40`                 | N — кількість віртуальних користувачів на сталому навантаженні |
| `RAMP_UP`         | `3m`                 | Наростання 0 → N                                              |
| `STEADY`          | `5m`                 | Стале навантаження з N користувачами                          |
| `RAMP_DOWN`       | `2m`                 | Спад N → 0                                                    |
| `THINK_TIME`      | `0.5`                | Максимальна пауза між запитами користувача, с (випадкова 0…max) |

### Підготовка бази

Сценарію потрібен непорожній каталог пристроїв. Сідер `catalog`
([`src/db/seeders/20261018210000-catalog.js`](../src/db/seeders/20261018210000-catalog.js))
створює адміністратора (`ADMIN_EMAIL`, `ADMIN_PASSWORD` з `.env`) і каталог пристроїв із
прошивками. Він входить у `npm run db:setup` (міграції + усі сідери, включно з демо-даними),
який задача ECS виконує перед стартом сервера. Як і міграції, кожен сідер виконується один раз
для бази (виконані записуються в таблицю `SequelizeData`), тому нові задачі під час
масштабування їх пропускають. Облікові дані Terraform бере з `.env` і передає задачі через SSM.
Локально — той самий `npm run db:setup`.

Швидка перевірка сценарію на локальному сервісі (у devcontainer):

```sh
PORT=3100 npm start &
BASE_URL=http://localhost:3100 VUS=3 RAMP_UP=5s STEADY=15s RAMP_DOWN=5s npm run loadtest
```

## Сценарій

Профіль «мало записів, багато читань»: одна ітерація віртуального користувача — **1 запис і
9 читань** (співвідношення 1:9). Аналогія з «постами»: запис — пристрій надсилає показання
(«створює пост»), читання — власник переглядає це показання, список показань і дані
пристрою-«автора».

| # | Запит                                         | Що імітує                                  |
|---|-----------------------------------------------|--------------------------------------------|
| 1 | `POST /ingest` (`X-Device-Key`)               | запис: нове показання                      |
| 2 | `GET /user-devices/:id/readings/:readingId`   | щойно створене показання за ідентифікатором |
| 3 | `GET /user-devices/:id/readings?limit=20`     | список показань                            |
| 4 | `GET /user-devices/:id`                       | дані автора (пристрій + модель + прошивка) |
| 5 | `GET /devices/:id`                            | модель пристрою з каталогу                 |
| 6 | `GET /user-devices`                           | список своїх пристроїв                     |
| 7 | `GET /devices`                                | каталог пристроїв                          |
| 8 | `GET /firmwares?deviceId=`                    | прошивки моделі                            |
| 9 | `GET /user-devices/:id/readings/:readingId`   | попереднє показання за ідентифікатором     |
| 10| `GET /user-devices/:id/readings?limit=20`     | повторне оновлення списку                  |

Між запитами — випадкова пауза 0…`THINK_TIME` с («час на роздуми» користувача). Список
показань — найчастіша операція читання (2 з 9), тому саме її буде кешовано в завданні 5.

**Підготовка (`setup`, виконується один раз, не входить у вимірювання).** Створюється
`ceil(N / 10)` тестових користувачів (`loadtest-<runId>-<i>@example.com`) і по одному
пристрою з ключем на кожного віртуального користувача. Реєстрація і вхід використовують
bcrypt (cost 12), тому їх свідомо винесено з циклу: інакше навантаження на процесор
визначалося б хешуванням паролів, а не профілем читань. Для пристроїв потрібна модель із
каталогу (береться перша наявна), тому перед першим прогоном на AWS каталог заповнюється
одноразово — див. «Підготовка бази» нижче.

**Фази.** Наростання 0 → N за 3 хв, стале навантаження N користувачів 5 хв, спад до 0 за
2 хв — разом 10 хв.

**Пороги** (k6 позначає їх ✓/✗ і повертає ненульовий код, якщо їх порушено):
`http_req_failed < 1 %`, `p95 < 500 мс`. Окремо для кожного запиту k6 звітує латентність
(тег `name`, щоб запити з різними ідентифікаторами групувалися).

### Вибір N

Один користувач робить ітерацію (10 запитів) приблизно за 2,5 с, тобто генерує близько
4 запитів/с. N підбирається так, щоб на сталому навантаженні середній CPU однієї задачі
(0,25 vCPU) перевищив цільові 50 % і спрацювало масштабування (завдання 1).

_Калібрування: значення N, за якого вперше спрацювало масштабування, і CPU однієї задачі._
