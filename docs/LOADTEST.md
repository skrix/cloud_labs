# Load test

Сценарій: [`loadtest/script.js`](../loadtest/script.js) (k6), запуск —
[`loadtest/run.sh`](../loadtest/run.sh).

## Запуск

```sh
npm run loadtest                       # BASE_URL береться з terraform output url
BASE_URL=http://<alb-dns> VUS=40 npm run loadtest
```

k6 (v1.8.2) встановлюється в devcontainer скриптом
[`.devcontainer/post-create.sh`](../.devcontainer/post-create.sh). Результати зберігаються в
`loadtest/results/<час>/`: `report.md` (підсумковий звіт) і `summary.json` (усі метрики k6,
не комітиться).

Перед тестом `run.sh` перевіряє, що сервіс і база доступні (`GET /api/health/db`): до 12 спроб
з інтервалом 5 с (після деплою задача ще може виконувати міграції та сідери), інакше
завершується з помилкою, не запускаючи k6.

| Змінна       | Типово                 | Опис                                                            |
|--------------|------------------------|-----------------------------------------------------------------|
| `BASE_URL`   | `terraform output url` | Адреса сервісу                                                  |
| `VUS`        | `40`                   | N — кількість virtual users (VU) на сталому навантаженні        |
| `RAMP_UP`    | `3m`                   | Наростання 0 → N                                                |
| `STEADY`     | `5m`                   | Стале навантаження з N користувачами                            |
| `RAMP_DOWN`  | `2m`                   | Спад N → 0                                                      |
| `THINK_TIME` | `0.5`                  | Максимальна пауза між запитами користувача, с (випадкова 0…max) |
| `HISTORY`    | `1440`                 | Історія показань кожного пристрою, яку завантажує `setup`       |
| `DEVICE_RATE` | `0` (вимкнено)        | Сценарій devices: показань за секунду на сталому навантаженні ([QUEUE.md](QUEUE.md)) |
| `DEVICES`    | `50`                   | Кількість пристроїв сценарію devices                            |

### Підготовка бази

Усі дані для прогону (користувачі, пристрої, історія показань) сценарій створює сам у `setup`.
Від бази потрібен лише каталог пристроїв: його створює сідер `catalog`
([`20261018210000-catalog.js`](../src/db/seeders/20261018210000-catalog.js)) разом з
адміністратором (`ADMIN_EMAIL`, `ADMIN_PASSWORD` з `.env`).

Сідери входять у `npm run db:setup` (міграції + усі сідери, включно з демо-даними), який задача
ECS виконує перед стартом сервера. Як і міграції, кожен сідер виконується один раз для бази
(виконані записуються в таблицю `SequelizeData`), тому нові задачі під час масштабування їх
пропускають. Облікові дані Terraform бере з `.env` і передає задачі через SSM. Локально — той
самий `npm run db:setup`.

Швидка перевірка сценарію на локальному сервісі (у devcontainer):

```sh
PORT=3100 npm start &
BASE_URL=http://localhost:3100 VUS=3 RAMP_UP=5s STEADY=15s RAMP_DOWN=5s npm run loadtest
```

## Сценарій

Профіль «мало записів, багато читань»: одна ітерація virtual user — **1 запис і
9 читань** (співвідношення 1:9). Аналогія з «постами»: запис — пристрій надсилає показання
(«створює пост»), читання — власник переглядає це показання, список і статистику показань і
дані пристрою-«автора».

| #  | Запит                                       | Що імітує                                   |
|----|---------------------------------------------|---------------------------------------------|
| 1  | `POST /ingest` (`X-Device-Key`)             | запис: нове показання                       |
| 2  | `GET /user-devices/:id/readings/:readingId` | щойно створене показання за ідентифікатором |
| 3  | `GET /user-devices/:id/readings?limit=20`   | список показань                             |
| 4  | `GET /user-devices/:id`                     | дані автора (пристрій + модель + прошивка)  |
| 5  | `GET /devices/:id`                          | модель пристрою з каталогу                  |
| 6  | `GET /user-devices`                         | список своїх пристроїв                      |
| 7  | `GET /devices`                              | каталог пристроїв                           |
| 8  | `GET /firmwares?deviceId=`                  | прошивки моделі                             |
| 9  | `GET /user-devices/:id/readings/:readingId` | попереднє показання за ідентифікатором      |
| 10 | `GET /user-devices/:id/readings/stats`      | статистика показань за 7 днів (по годинах)  |

Між запитами — випадкова пауза 0…`THINK_TIME` с («час на роздуми» користувача). Статистика —
найважча операція читання: сервіс читає всі показання пристрою за період (≈ `HISTORY` + нові) і
агрегує їх у JavaScript, тож саме вона визначає навантаження на CPU і її варто кешувати в
завданні 5.

**Підготовка (`setup`, виконується один раз, не входить у вимірювання).** Створюється
`ceil(N / 10)` нових користувачів (`loadtest-<runId>-<u>@example.com`) і по одному пристрою з
ключем на кожного virtual user; кожен пристрій одразу завантажує історію з
`HISTORY` показань пакетами по 1000 (`POST /ingest` з масивом). Реєстрація і вхід використовують
bcrypt (cost 12), тому їх свідомо винесено з циклу: інакше навантаження на CPU визначалося б
хешуванням паролів, а не профілем читань. Кожен прогін починає з однакових даних і не залежить
від попередніх; дані прогонів лишаються в базі (≈ N × `HISTORY` рядків за прогін).

**Сценарій devices** (лише з `DEVICE_RATE > 0`, для завдання 6). Паралельно з користувачами
`DEVICES` пристроїв окремого користувача надсилають показання (`POST /ingest`) зі швидкістю до
`DEVICE_RATE` за секунду в тих самих трьох фазах (executor `ramping-arrival-rate`). Він створює
чергу записів, від довжини якої масштабується worker. Метрики сценарію звітуються окремо
(тег `scenario:devices`).

**Запис через чергу.** Коли `POST /ingest` відповідає 202, показання з'являється в базі лише
після worker, тому читання щойно записаного показання (запит 2) і попереднього (запит 9)
приймає 200 або 404 і рахує частку вже доступних (`reading_visible_now`,
`reading_visible_next_iteration`). `setup` чекає, доки worker збереже історію пристроїв.

**Фази.** Наростання 0 → N за 3 хв, стале навантаження N користувачів 5 хв, спад до 0 за
2 хв — разом 10 хв.

**Вимірювання** лише фази навантаження: thresholds і звіт беруть метрики з тегом
`scenario:users`, тож запити `setup` (реєстрація, пристрої, історія) у них не потрапляють.

**Thresholds** (k6 позначає їх ✓/✗ і повертає ненульовий код, якщо їх порушено):
`http_req_failed < 1 %`, `p95 < 500 мс`. Окремо для кожного запиту k6 звітує latency
(тег `name`, щоб запити з різними ідентифікаторами групувалися).

### Вибір N

Один користувач робить ітерацію (10 запитів) приблизно за 2,5 с, тобто генерує близько
4 запитів/с. N підбирається так, щоб на сталому навантаженні середній CPU однієї задачі
(0,25 vCPU) перевищив target 70 % і спрацювало масштабування (завдання 1).

Калібрування (одна задача, 0,25 vCPU):

| Прогін             | Версія                                                   | N   | CPU на сталому навантаженні | Масштабування                                |
|--------------------|----------------------------------------------------------|-----|-----------------------------|----------------------------------------------|
| `20261108T222156Z` | без статистики, target 60 %                              | 40  | 50–59 %                     | ні                                           |
| `20261109T224400Z` | без статистики, target 50 %                              | 40  | 59–65 %                     | так, але лише на спаді                       |
| `20261110T100143Z` | статистика за 30 днів засіяної історії, target 70 %      | 60  | 85–100 % (насичення)        | так, desired 2 на сталому (10:08:32)         |
| `20261110T105034Z` | статистика, історія 1440 показань у `setup`, target 70 % | 100 | 99–100 % (насичення)        | так, desired 2 наприкінці сталого (10:58:32) |

Поточна версія легша в розрахунку на ітерацію (уся історія — в одній годині, тож статистика має
один інтервал замість 720), тому N = 40–60 її не насичує і потрібно N ≈ 100. Перетин порогу настає
вже на наростанні, а нова задача з'являється через ≈ 5,5 хв — наприкінці сталої фази.

## Результати

Прогін `loadtest/results/20261110T105034Z` — поточна версія сценарію, N = 100, target 70 %
([звіт](../loadtest/results/20261110T105034Z/report.md)):

| Показник           | Значення                                        |
|--------------------|-------------------------------------------------|
| N (virtual users)  | 100                                             |
| Кількість запитів  | 85 780 (8 578 ітерацій)                         |
| Запитів за секунду | 131 у середньому; ≈ 160 на сталому навантаженні |
| Частка помилок     | 0,00 %                                          |
| Latency p50        | 254 мс                                          |
| Latency p95        | 599 мс (поріг 500 мс — ✗)                       |
| Latency p99        | 872 мс                                          |
| Максимум задач ECS | 3                                               |

Поріг p95 не витримано: близько 5 хвилин (від перетину порогу о 10:53 до появи другої задачі
о 10:58:32) уся робота лягала на одну насичену задачу (CPU 100 %), і запити стояли в черзі —
саме цю затримку масштабування описано в [AUTOSCALING.md](AUTOSCALING.md).

Помилки — лише дві відповіді 502 від load balancer (10:56 і 11:00): 2 з 85 780 запитів
(0,002 %), тому у звіті 0,00 %. Це проблема keep-alive, виправлена в `src/server.js`, але ще не
розгорнута.
