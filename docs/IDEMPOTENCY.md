# Idempotency

`POST /ingest` приймає заголовок **`Idempotency-Key`**: перший запит із ключем виконується, а
відповідь зберігається в Redis на 24 години; повтор із тим самим ключем повертає збережену
відповідь **без повторного виконання** — нічого не пише в базу і не кладе в чергу.

Код: [`src/idempotency.js`](../src/idempotency.js), [`src/routes/ingest.js`](../src/routes/ingest.js).
Тести: [`test/api/idempotency.test.js`](../test/api/idempotency.test.js),
[`test/idempotency.test.js`](../test/idempotency.test.js).

## Яку проблему це розв'язує

Сервіс записав показання, але відповідь загубилась (обрив Wi-Fi, таймаут, 502, задачу зняв
scale-in). Пристрій бачить збій і повторює запит — без захисту показання запишеться **двічі**, і
статистика (count, avg, p95) спотвориться. IoT-пристрої в ненадійних мережах повторюють запити
автоматично.

GET, HEAD, OPTIONS, PUT, DELETE ідемпотентні за визначенням: повтор дає той самий стан сервера.
**POST** — ні: кожен виклик створює новий ресурс. Клієнт генерує ключ (UUID) **один раз на
операцію** і надсилає його в кожній спробі — за ключем сервіс розпізнає повтор.

## Як це працює

```
POST /ingest  Idempotency-Key: K
  SET idempotency:ingest:<хеш ключа пристрою>:K {in-progress} NX EX 60
  ├─ встановлено → виконати запит
  │    ├─ успіх   → зберегти відповідь на 24 год, повернути її
  │    └─ помилка → видалити ключ (повтор виконається), повернути помилку
  └─ ключ уже є
       ├─ інше тіло запиту → 422
       ├─ in-progress      → 409 (перший запит ще виконується)
       └─ done             → збережена відповідь + Idempotent-Replayed: true
```

- **`SET NX` атомарний**: із двох одночасних однакових запитів виконується лише один.
- **Зберігається вся відповідь** (статус, тіло, `Location`) — повтор отримує ті самі `id`.
- **Ключ прив'язаний до пристрою**: однакові ключі різних пристроїв не перетинаються.
- **Той самий ключ з іншим тілом — `422`**: це помилка клієнта, мовчки повернути стару відповідь
  було б неправильно.
- **`in-progress` живе 60 с** — якщо задача впала посеред запиту, ключ не заблокований на добу.
- **Ключ необов'язковий**; невалідний (не 1–255 видимих символів ASCII) — `400`.

**Чому Redis.** Повтор може потрапити на іншу задачу API, тож ключі мають бути спільними —
пам'ять процесу не підходить ([CACHE.md](CACHE.md)). Redis уже є, дає атомарний `SET NX` і TTL
без окремого прибирання; працює і з вимкненим кешем.

**Якщо Redis недоступний**, запит виконується без перевірки ключа (fail open): прийняти
показання важливіше, ніж захиститися від рідкісного повтору саме в цей момент.

## Тест

`test/api/idempotency.test.js` — через HTTP API з реальною PostgreSQL:

| Тест                                                                     | Перевіряє                                |
|--------------------------------------------------------------------------|------------------------------------------|
| two identical requests: one reading stored, two identical responses      | **1 запис у базі, 2 однакові відповіді** |
| replays a batch as a whole                                               | пакет із 3 показань — 3 записи, не 6     |
| stores each request with a different key or without a key                | різні ключі / без ключа записуються      |
| keeps the same key of two devices apart                                  | ключ прив'язаний до пристрою             |
| rejects the same key with a different body with 422                      | повторне використання ключа              |
| rejects an invalid key with 400                                          | валідація ключа                          |
| does not keep a failed request, so a retry with the same key can succeed | помилка не зберігається                  |

`test/idempotency.test.js` перевіряє `409`, звільнення ключа після помилки і роботу без Redis;
`test/api/ingest-queue.test.js` — що повтор із тим самим ключем дає **одне** повідомлення в черзі.

Вручну в AWS (відповідь `202`, бо працює черга):

```sh
API=$(terraform -chdir=deploy/aws/terraform output -raw url)/api
for i in 1 2; do
  curl -si -X POST "$API/ingest" -H 'Content-Type: application/json' \
    -H "X-Device-Key: $DEVICE_KEY" -H 'Idempotency-Key: demo-001' -d '{"temperature":21.5}' \
    | grep -iE '^(HTTP|location|idempotent)'
done
```

## Як поєднується з чергою (завдання 6)

Дублікати можуть з'явитися на двох ділянках, і кожну закриває свій механізм:

```
пристрій ──(1) повтор HTTP──▶ API ──(2) повторна доставка SQS──▶ worker ──▶ PostgreSQL
           Idempotency-Key            id від API + ON CONFLICT DO NOTHING
```

1. **Пристрій → API.** Без ключа повтор отримав би нові `id` і створив **друге** повідомлення —
   worker вважав би його іншим показанням. З ключем повтор отримує той самий `202` з тими самими
   `id` і `Location`, а в черзі лишається одне повідомлення.
2. **API → worker.** SQS може доставити повідомлення двічі; ідемпотентний worker
   ([QUEUE.md](QUEUE.md)) другу копію ігнорує, бо `id` той самий.

Разом показання записується рівно один раз; окремо жоден механізм цього не гарантує.

**Залишкове вікно**: якщо задача API впала після `SendMessage`, але до збереження відповіді, ключ
звільниться через 60 с, і повтор дасть нові `id`. Закрити його можна, виводячи `id` з ключа
(UUID v5 від пристрою, ключа і номера в пакеті).
