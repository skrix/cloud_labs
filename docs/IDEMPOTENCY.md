# Idempotency

Операція запису `POST /ingest` приймає заголовок **`Idempotency-Key`**: перший запит із ключем
виконується, а його відповідь зберігається в Redis на 24 години; повторний запит із тим самим
ключем повертає збережену відповідь **без повторного виконання** — нічого не записує в базу і не
кладе в чергу.

Код: [`src/idempotency.js`](../src/idempotency.js), [`src/routes/ingest.js`](../src/routes/ingest.js).
Тести: [`test/api/idempotency.test.js`](../test/api/idempotency.test.js),
[`test/idempotency.test.js`](../test/idempotency.test.js).

## Яку проблему це розв'язує

Клієнт не завжди дізнається, чи виконався його запит. Пристрій надіслав показання, сервіс його
записав, але відповідь загубилась: обрив Wi-Fi, таймаут клієнта, перезапуск задачі API під час
scale-in, 502 від load balancer. Для пристрою це виглядає як збій, і він повторює запит. Без
захисту показання запишеться **двічі**: у списку з'являться дублікати, а статистика (count,
avg, p95) буде спотворена.

Методи HTTP **GET, HEAD, OPTIONS, PUT, DELETE** ідемпотентні за визначенням: повтор дає той самий
стан сервера. **POST** — ні: кожен виклик створює новий ресурс. `Idempotency-Key` робить POST
безпечним для повтору: клієнт генерує ключ (наприклад, UUID) **один раз на операцію** і
надсилає його в кожній спробі цієї операції. Сервіс за ключем розпізнає повтор.

Для IoT це особливо важливо: пристрої працюють у ненадійних мережах і повторюють запити
автоматично, часто з буфера показань, накопичених офлайн.

## Як це працює

```
POST /ingest  X-Device-Key: …  Idempotency-Key: K
  1. SET idempotency:ingest:<sha256(X-Device-Key)>:K  {in-progress, fingerprint}  NX EX 60
     ├─ встановлено (ключа ще не було) → виконати запит
     │     ├─ успіх   → SET … {done, fingerprint, відповідь} EX 86400, повернути відповідь
     │     └─ помилка → DEL …  (ключ звільнено, повтор виконається), повернути помилку
     └─ ключ уже є → прочитати
           ├─ інше тіло запиту (fingerprint)  → 422
           ├─ in-progress                     → 409 (перший запит ще виконується)
           └─ done                            → збережена відповідь + Idempotent-Replayed: true
```

- **Атомарне захоплення ключа** (`SET … NX`): з двох одночасних однакових запитів виконується
  лише один, другий отримує `409` і може повторити пізніше. Без `NX` обидва побачили б «ключа
  немає» і обидва записали б показання.
- **Зберігається вся відповідь** — статус (`201` або `202`), тіло і `Location`. Повтор отримує
  ті самі `id` показань, що й перша спроба.
- **24 години** (`IDEMPOTENCY_TTL_SECONDS`, типово 86 400): довше, ніж будь-який розумний цикл
  повторів клієнта; Redis сам видаляє ключ після TTL.
- **Ключ прив'язаний до пристрою** (хеш `X-Device-Key`): однаковий ключ двох пристроїв —
  незалежні операції, і один пристрій не може отримати чужу відповідь.
- **Той самий ключ з іншим тілом — `422`.** Це помилка клієнта (ключ використано повторно для
  іншої операції); мовчки повернути стару відповідь було б неправильно. Тіло порівнюється за
  SHA-256 від JSON.
- **Невдалий запит не зберігається** (`400`, `401`, `413`, `5xx`): ключ звільняється, щоб
  виправлений або повторений запит міг виконатися.
- **`in-progress` живе 60 с**: якщо задача API впала посеред запиту, ключ не заблокований на
  24 години.
- **Ключ необов'язковий**: без нього запит виконується як раніше. Невірний ключ (порожній,
  довший за 255 символів, не ASCII) — `400`.

**Чому Redis.** Ключі мають бути спільними для всіх задач API: повтор може потрапити на іншу
задачу (load balancer), тож пам'ять процесу не підходить (так само, як для кешу,
[CACHE.md](CACHE.md)). Redis уже є (завдання 5), дає атомарний `SET NX` і TTL без окремого
прибирання. Redis для ключів спільний із кешем, але працює і з вимкненим кешем
(`cache_enabled = false`).

**Якщо Redis недоступний**, запит виконується без перевірки ключа (fail open, з помилкою в
журналі): запис показань важливіший, ніж захист від рідкісного повтору саме в цей момент.
Протилежний вибір (fail closed, `503`) гарантував би відсутність дублікатів ціною відмови в
записі на час збою Redis.

## Тест

`test/api/idempotency.test.js` — через HTTP API з реальною PostgreSQL і Redis-заглушкою в
пам'яті (`SET NX/EX`, `GET`, `DEL`):

| Тест                                                                         | Перевіряє                                           |
|------------------------------------------------------------------------------|-----------------------------------------------------|
| two identical requests: one reading stored, two identical responses          | **1 запис у базі, 2 однакові відповіді**, `Idempotent-Replayed: true` у другій |
| replays a batch as a whole                                                   | пакет із 3 показань — 3 записи, не 6               |
| stores each request with a different key or without a key                    | різні ключі / без ключа — кожен запит записується |
| keeps the same key of two devices apart                                      | ключ прив'язаний до пристрою                       |
| rejects the same key with a different body with 422                          | повторне використання ключа                        |
| rejects an invalid key with 400                                              | валідація ключа                                    |
| does not keep a failed request, so a retry with the same key can succeed     | помилка не зберігається                            |

`test/idempotency.test.js` — логіка окремо: `409` поки перший запит виконується, звільнення
ключа після помилки, TTL 24 год, робота без ключа / без Redis / зі збоєм Redis.
`test/api/ingest-queue.test.js` — з чергою: повтор із тим самим ключем дає **одне**
повідомлення в черзі і ті самі `id`.

Додатково перевірено локально з реальним Redis 7.4:

```
POST /ingest  Idempotency-Key: demo-001  → 201 Created
POST /ingest  Idempotency-Key: demo-001  → 201 Created, Idempotent-Replayed: true (тіло ідентичне)
POST /ingest  Idempotency-Key: demo-001, інше тіло → 422
GET  …/readings → 1 показання;  TTL ключа в Redis → 86400
```

Те саме в AWS (API відповідає `202`, бо працює черга):

```sh
API=$(terraform -chdir=deploy/aws/terraform output -raw url)/api
for i in 1 2; do
  curl -si -X POST "$API/ingest" -H 'Content-Type: application/json' \
    -H "X-Device-Key: $DEVICE_KEY" -H 'Idempotency-Key: demo-001' -d '{"temperature":21.5}' \
    | grep -iE '^(HTTP|location|idempotent)'
done
```

## Як поєднується із завданням 6 (черга)

Черга й `Idempotency-Key` закривають **дві різні ділянки** шляху показання, і разом дають
ефект «рівно один раз» від пристрою до бази:

```
пристрій ──(1) повтор HTTP──▶ API ──(2) повторна доставка SQS──▶ worker ──▶ PostgreSQL
           Idempotency-Key            id від API + ON CONFLICT DO NOTHING
```

1. **Пристрій → API.** Якщо загубилась відповідь `202`, пристрій повторює запит. Без ключа API
   створив би **нові** `id` і поклав у чергу **друге** повідомлення — ідемпотентний worker тут
   не допоможе, бо для нього це інше показання. З ключем повтор отримує збережену відповідь
   `202` з тими самими `id` і `Location`, а в черзі лишається **одне** повідомлення.
2. **API → worker.** SQS доставляє «щонайменше один раз»: те саме повідомлення може прийти
   двічі. Це закриває ідемпотентний worker ([QUEUE.md](QUEUE.md)): `id` призначає API, і
   друга вставка з тим самим `id` нічого не додає.

Тобто `Idempotency-Key` гарантує, що одна операція клієнта породжує **одне** повідомлення з
**фіксованими** `id`, а ідемпотентний worker — що одне повідомлення дає **один** запис, скільки б
разів його не доставили. Окремо жоден механізм дублікатів не усуває.

З чергою ключ корисний ще й тим, що відповідь `202` повертає `id` і `Location`: клієнт, який
повторив запит, опитує ту саму адресу, а не адресу «другого» показання.

**Залишкове вікно.** Якщо задача API впала після `SendMessage`, але до збереження відповіді,
ключ лишиться `in-progress` і через 60 с звільниться — повтор після цього створить нові `id`.
Закрити й це вікно можна, виводячи `id` показання з ключа, а не випадково (наприклад, UUID v5
від `пристрій + Idempotency-Key + номер у пакеті`): тоді навіть повторне виконання дасть ті самі
`id`, і worker відкине дублікат.
